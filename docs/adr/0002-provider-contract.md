# ADR 0002 — プロバイダーの契約: 信頼境界、承認した 1 操作の許可、能力の宣言、版の指定

- 状態: Accepted（2026-11-10 に合意。段階 1・2a・2b、段階 3 の Pome による配布は実装済み）
- 日付: 2026-11-10
- 対象: Proxmox と mamelet の次に、外部の開発者が書くプロバイダー（AWS など）

## 文脈

これまでのプロバイダーは、Mamela のリポジトリの中にあるコードだけだった。外部の開発者がプロバイダーを書き、使う人が版を指定して使えるようにしたい。そのためには、Mamela の安全性（最小権限、宣言していないことはしない、削除は既定で拒否、結果が分からないときは観測してから続ける）を、Mamela が書いていないコードに対しても保つ方法を決める必要がある。

この ADR の最初の版には、次の誤りがあった。この版で直した。

- 「資格情報を渡さなければ、プロバイダーは何もできない」と書いていた。ふつうのネイティブプロセスは、使う人のファイルや環境変数を読める。EC2 の上では、メタデータから資格情報を取れることもある。したがって、信頼境界を先に決めなければならない。
- マニフェストに書いた呼び出しとパラメータ名に限るだけで、承認した台数・対象・値を越えられた。
- 「効果」をプロバイダーの自己申告のまま、安全の判断に使おうとしていた。
- `ErrNotSent` を「何も起きていない」と書いていた。保証できるのは、送らなかったその 1 つの要求についてだけである。
- 付与の条件が文字列で、機械的に検査できなかった。
- 承認した plan が、どの版のプロバイダーに対するものかを持っていなかった。

## 決定

### 1. 信頼境界: プロバイダーは信頼しないコードとして、隔離して実行する

外部のプロバイダーは、**信頼しないコード**として扱う。安全性は、プロバイダーが正しく書かれていることに頼らない。次のことだけに頼る。

- 隔離
- host の検査
- 外部の権限の仕組み（Proxmox の ACL、AWS の IAM）

**既定の形式は WASM にする。** Mamela がすでに評価に使っている、固定版の wasmtime で実行する。ディレクトリ、環境変数、ネットワーク、HTTP は与えない。プロバイダーが外と話せる道は、stdin と stdout の JSON-RPC だけになる。import は実行前に許可リストで確かめる（`internal/provider/host`）。

| 形式 | 許す import |
|---|---|
| WASI 0.3 component | `wasi:cli` の stdin・stdout・stderr・exit・types だけ |
| WASI preview 1 の core module（Go の `GOOS=wasip1`） | stdio、引数と環境変数（どちらも空）、時計、乱数、yield、exit。`path_*`（ファイル）と `sock_*`（ソケット）は拒否する |

preview 1 を受け付けるのは、Go が出せる WASM がこれだけだからである。時計と乱数は Go の実行時が必要とするので与えるが、どちらも外への道ではない。diff が入力だけから決まることは、時計を取り上げることではなく、適合テスト（同じ入力で 2 回 diff して比べる）と、diff の間は要求を一切通さないことで確かめる。外部 API への要求も、この道で host に頼む（`host/request`）。したがって、次のことが成り立つ。

- プロバイダーは、資格情報、使う人のファイル、メタデータのエンドポイントのどれにも届かない。
- 外への要求は、すべて host を通り、host が検査して記録する。
- 隔離は OS によらない（macOS でも Linux でも同じ）。

host は、検査した実行ファイルのバイト列を、自分だけが読めるディレクトリに写してから、その写しを実行する。検査の後にパスの先を差し替えても、差し替えたものは動かない。

**ネイティブの実行ファイルは、信頼する場合だけ使える。** 使う人が、そのプロバイダーの source path と版と実行ファイルの digest を指定して「信頼する」と明示したときに限る（`mamela provider trust`。記録は、レビューできるファイルに残す）。そのとき Mamela は、次のことを表示する。「このプロバイダーは、あなたのファイル、環境変数、ネットワーク（EC2 のメタデータを含む）に届く。Mamela の検査は誤りを防ぐもので、悪意を防ぐものではない。」環境変数を空にし、作業ディレクトリを専用にするなどの最小化は行うが、それを安全の根拠にはしない。

**hash の固定は改変の検出であり、安全の証明ではない。** Pome の依存を足しても、それだけでプロバイダーを実行することは許されない。

- WASM のプロバイダー: 初めて使うときに、マニフェスト（扱う種類、能力、外部 API の範囲）を表示し、使う人の確認を取る。
- ネイティブのプロバイダー: 上の「信頼する」の明示がなければ実行しない。

### 2. 承認した 1 操作だけを実行できる: 操作の許可（permit）

host は、承認した plan の操作を 1 つ実行するたびに、その操作だけの許可（permit）を発行する。プロバイダーの `apply` と、その間の `host/request` は、すべてこの許可に結びつく。

| 許可の項目 | 内容 |
|---|---|
| operation ID、plan の digest、プロバイダーの digest | 何の承認による実行か |
| 対象 ID | パスの ID（Proxmox の node・vmid・storage、AWS のリソース ID や ARN）。作成時に決まる ID は、host が決める（予約）か、作成の応答から host が記録して結びつける |
| 呼び出し | マニフェストのうち、その操作の呼び出しだけ。各パラメータを、クエリとフォームのどちらで送るかも宣言する |
| 変更の要求 | 変更の要求は、承認した要求（`Change.Requests`）のどれかと、パラメータの名前と値がすべて一致しなければならない。省略・追加・別の値は拒否する。承認した要求は 1 回だけ送れる |
| 前提条件 | 対象の観測の版（Proxmox の config digest、AWS のタグや状態）。違えば送らない。host が強制するのは、host のカタログがその呼び出しに前提条件のパラメータ（`version`、`digest` など）を書いているときである |
| 期限と回数 | 期限つきで、一度きり。操作が終わったら無効にする |

パラメータは、host のカタログが「API がそこから読む」と書いた場所（クエリかフォーム）でしか送れない。host が確かめた値と、API が使う値を一致させるためである（例: フォームの版を読む API に、版をクエリで送って前提条件を逃れることはできない）。

許可は、承認した変更（`protocol.Change`）とマニフェストから `protocol.NewPermit` で導く。host は、渡された許可が導いたものと一致することを確かめる。呼び出しを足した許可や、別の対象を書いた許可は、実行の前に拒否する。

`observe` の間は、変更の要求を一切受け付けない（読み取りだけ）。`diff` の間は、外部への要求そのものを受け付けない（`diff` は入力だけから計算する）。許可に合わない要求は送らずに拒否し、記録する。

同じ apply の中で、次のことが起きたら、それ以降の変更の要求をすべて拒否する。

- 変更の要求の結果が分からなくなった
- 要求を 1 つ拒否した

二重に実行しないように、観測からやり直す。host は HTTP のリダイレクトに従わない。リダイレクト先は、host が確かめた要求ではないからである。

**段階 2a の外部プロバイダー（`internal/provider/host`）での実装:** 上の表のすべてを、`host/request` ごとに確かめる。

- **確かめないこと:**
  - 読み取りの要求のパラメータの値（名前と場所は確かめる）
  - フォーム以外の本文（v1 の `host/request` は、クエリとフォームしか送れない）
  - 許した要求を受けて、API がカタログの効果以上のことをするかどうか
  - apply 中の読み取りの対象
  - カタログが前提条件のパラメータを書いていない呼び出しの前提条件
- **一度きり:** 段階 2a では、同じセッションの中で確かめる。プロセスをまたぐ記録（SQLite）は段階 2b で加える。

**段階 1 の Proxmox（in-process）での実装:** `proxmox.RestrictOperation`、`Bind`、`Values`、`ReadOnly`。

- **確かめること:**
  - 宣言した呼び出しとパラメータ名
  - パスの ID（node・vmid・storage）
  - 値（作成の name・cores・memory・pool、設定の cores・memory・tags、拡張の disk・size）
  - 観測中に変更の要求を送らないこと
- **確かめないこと:**
  - 固定していないほかの値
  - アップロードの中身（イメージは別に sha256 で照合している）
  - Proxmox の config digest 以外の前提条件
  - 読み取りの対象

この境界は、`internal/proxmox/restrict.go` の冒頭にも書いた。

### 3. 効果: host が検証できる効果と、作者の申告を分ける

操作の効果（作成、その場で変える、再起動する、データを失いうる、置き換える）には、2 つの出どころがある。

- **host が検証した効果:** host が持つ API のカタログから導く。たとえば、Proxmox のカタログに Mamela が書いた「この呼び出しは何をするか」や、AWS の Service Authorization Reference の access level に、Mamela が持つ「データを失いうる action」の一覧を加えたもの。許可（決定 2）で、実際に送る要求はこのカタログの範囲に限られる。そのため、操作の効果は、送りうる要求の効果を合わせたもので上から抑えられる。
- **作者が申告した効果:** マニフェストに書いた効果。表示とレビューの助けにするが、安全の判断には使わない。

規則:
- **自動で承認してよいのは、host が検証した効果がすべて、policy が自動を許す範囲にあるときだけ。** host が分類できない要求を 1 つでも含む操作は、つねに人の承認が要る。
- 検証した効果に「データを失いうる」が含まれる操作は、既定で拒否する（今の shrink や replace と同じ）。申告が「その場で変える」でも、検証した効果が優先する。
- **共通の効果分類は要約にすぎない。** 新しいプロバイダーの変更の意味（diff）は、host には分からない。人がレビューするのは diff と、許可が固定する値である。apply の後は、つねに再観測して、宣言どおりかを確かめる。

### 4. 結果: 1 つの要求と操作全体を区別し、部分的な成功から観測して戻る

- `ErrNotSent` は、送らなかったその 1 つの要求について、何も起きていないことだけを保証する。
- 操作全体の結果は 4 つある。

  | 結果 | 意味 |
  |---|---|
  | done | 操作が完了した |
  | failed | 変更の要求が 1 つも効いていない |
  | partly-done | いくつかの変更が効いた（または効いたかもしれない）あとで失敗した（`reconcile.ErrPartlyDone`、MAM-REC-0006） |
  | unknown | 結果が分からない |

- **host が変更の要求を記録する。** `host/request` を通るので、どの変更の要求が効いたかは host が知っている。プロバイダーの申告には頼らない。in-process の Proxmox では、`proxmox.Changed` がこの記録を持つ。
- **結果の判定（段階 2a）:** host は、記録だけから結果を決める。
  - 分類できない要求と、カタログで読み取りでない要求は、変更として扱う。
  - 変更の要求が送られて結果が分からない（応答がない、または 5xx）ものが 1 つでもあれば、unknown にする。プロバイダーが成功と答えても同じである。
  - 許可を越えた要求が 1 つでもあれば、プロバイダーの答えにかかわらず、その apply は失敗として扱う。
  - 変更の要求が API に拒否された、または送れなかったのに、プロバイダーが成功と答えたときも、成功として扱わない（failed か partly-done）。
- **partly-done と unknown のとき、次の apply は観測してから動く。** プロバイダーは、`lookup`（変更が効いているかを、読み取りだけで調べる）と、途中からの続き（できていることは飛ばす）を実装しなければならない。これは適合テスト `provider/providertest` で確かめる。

### 5. 条件は最初から型付きにする

能力（`spec.Need`）は、次のものを持つ。

- **付与の期間 `grant`:** `once`（承認した 1 操作）または `standing`。`standing` は、`standingIf` の条件が成り立つときだけ認める。
- **型付きの条件 `conditions`:** `{key, test, values}` の形で書く。

  | 項目 | 内容 |
  |---|---|
  | `key` | 名前空間を持つ。`mamela:node`、`mamela:operation`、`mamela:now`、`mamela:apt.changeSet`、`mamela:apt.remove`、`mamela:apt.origin`、`mamela:policy.autoStartServices`。AWS の条件キー（`aws:RequestTag/...`、`ec2:InstanceType` など）も同じ形で書く |
  | `test` | IAM の演算子に合わせる。equals、in、like、before、contains、notPresent |
  | `values` | 値そのものか、テンプレート（`{node}`、`{changeSet}`、`{operationId}`、`{expiresAt}`）。決まっていない値が残る条件は成り立たない |

- **説明 `note`:** 人向けの説明は `note` に分ける。何も検査しない。

条件を誰が強制するかは、条件の種類で分かれる。

- **mamelet:** 署名した revision の中の条件。
- **host:** `host/request` の許可。
- **AWS:** IAM のセッションポリシー。`mamela:` 以外の条件キーは、そのまま IAM の Condition ブロックに写す。

### 6. 承認した plan は、プロバイダーの契約に結びつく

plan の入力に、プロバイダーの digest（`ProvidersDigest`）を含める。今はマニフェスト全体の正規形の digest である。段階 2 からは、プロバイダーごとに次のものを加える。

- source path
- 版
- プロトコルの版
- マニフェストの digest
- 実行ファイル（WASM またはネイティブ）の digest
- 信頼の種類

apply は、今のプロバイダーの digest が plan と違えば何も実行しない（MAM-REC-0007）。プロバイダーや Mamela を更新すると、承認は効かなくなり、新しい plan と承認が要る。

### 7. 版の指定とプロトコル（段階 2 以降。方向は前の版から変えない）

- **版の指定:** Pome.toml の依存で指定する。Pome.lock と sumdb から、Pome の中の `provider.lock`、そして実行ファイル（WASM またはプラットフォームごとのネイティブ）の sha256 まで、hash の鎖をつなぐ。ただし、この鎖が保証するのは改変されていないことだけである。実行してよいかは、決定 1 の確認で決める。
- **プロトコル（`mamela-provider-rpc/v1`、段階 2a で実装）:** stdin と stdout で JSON-RPC 2.0 を話す。1 行に 1 つのメッセージを書く。host は一度に 1 つの要求を送り、その応答を待つ間だけ、プロバイダーからの `host/request` を受け付ける。メソッドは次のとおり。

  | メソッド | 内容 |
  |---|---|
  | `describe` | マニフェストを返す |
  | `observe` | 読み取りの要求だけで実状態を返す |
  | `diff` | 外部への要求なしで差分と操作を返す |
  | `apply` | 許可（permit）とともに 1 操作を実行する |
  | `lookup` | 変更が効いているかを、読み取りだけで調べる（done・not-done・partly-done） |
  | `host/request` | 外部 API への要求を host に頼む（許可に結びつく） |

  資格情報は host だけが持つ。host が、Proxmox のトークンを付けるか、AWS の SigV4 で署名する。AWS では、plan ごとに必要な action・resource・条件だけを許すセッションポリシーを付けた、短期の資格情報を使う。

### 8. 段階

1. **実装済み**
   - in-process のマニフェスト（`spec`）と、宣言のリソースごとの分析
   - `mamela check --json`
   - Proxmox の操作の許可: 呼び出し・ID・値・観測中は読み取りのみ
   - partly-done
   - 型付きの条件（mamelet の許可: ノード・操作・期限・変更集合・削除なし・origin）
   - plan とプロバイダーの digest の結びつき
2. **段階 2a（信頼境界と許可の契約）: 実装済み**
   - 公開パッケージ `provider/protocol`（マニフェスト、JSON-RPC、許可、カタログ）と、Go の SDK `provider/sdk`
   - WASM のプロバイダーの実行（import の許可リスト、stdio だけ）
   - `host/request` の許可（permit）の検査
   - host による変更の記録と、4 つの結果の判定
   - host のカタログによる効果の検証（`Verified.AutoApprovable`、`MayLoseData`）
   - ネイティブを信頼するための明示（`mamela provider trust`、`mamela.trust.toml`）
   - プロバイダー作者向けの適合テスト `provider/providertest`
   - 例のプロバイダー `examples/kv`
3. **段階 2b（Mamela の流れにつなぐ）: 実装済み**
   - `mamela-graph/v2`: プロバイダーの種類のリソース（`provider` と、解釈しない spec）
   - plan: プロバイダーの観測と diff を、スナップショットに記録する（apt のシミュレーションと同じ扱い）。plan は、承認する変更の要求をパラメータまで持つ。プロバイダーのプログラムを SQLite に保存する
   - apply: plan と同じプログラムを動かす。新しい diff が承認した変更と完全に同じときだけ実行する。許可の一度きりを SQLite に記録する
   - policy: 効果の検証で判定する（データを失いうる → 拒否、分類できない → 承認、`autoProviderEffects` → 自動）
   - plan の digest に、プロバイダーの実行ファイルの digest とプロトコルの版を加えた
   - 残り: 今の Proxmox と mamelet を、この契約の上に移す。Proxmox のカタログを host のカタログにする
4. **段階 3**
   - Pome による配布と版の指定: 実装済み。Pome に `mamela-provider.toml` と WASM のプログラムを入れる。`provider.lock` は作らず、Pome.lock と sumdb の hash の鎖をそのまま使う。宣言で import する
   - 残り: `pome/mamela` v0.2.0 と例のプロバイダーの Pome の公開
5. **段階 4**
   - AWS（EC2 の VM）。ARN と条件キーによる能力と、セッションポリシーによる最小の付与
   - エディタ向けの `mamela lsp`

まず信頼境界と許可の契約を固め、その後に配布と AWS に進む。そうすれば、外部の作者に「何を実装すれば Mamela の安全性を保てるか」を、適合テストとして示せる。

## 見送った案

- **ネイティブのプロバイダーを、資格情報を渡さないことだけで守る。** 成立しない（文脈を参照）。
- **OS のサンドボックス（Linux の namespace・seccomp・Landlock、macOS の sandbox-exec）を、既定の隔離にする。** OS ごとに実装と保証が異なり、macOS の sandbox-exec は非推奨である。WASM なら、Mamela がすでに固定して検証している wasmtime で、同じ隔離をどこでも得られる。ネイティブの実行を、信頼する場合の上に OS のサンドボックスで重ねることは、後で検討する。
- **実装から呼び出しの一覧を自動で導く。** 条件つきの呼び出しを網羅できず、漏れが黙って起きる。宣言を正とし、越えたら送る前に止める（決定 2）。
- **プロバイダーが申告する効果で、自動の承認を決める。** 申告は検証できない（決定 3）。
- **gRPC。** JSON-RPC over stdio は、WASM の stdio とそのまま合う。依存も少なく、データが `mamela check --json` と同じ形になる。

## 未解決

- WASM のプロバイダーを書く言語と SDK: 段階 2a では Go（wasip1）の SDK を用意した。Rust（wasip2）は、今の component の許可リストでは std の import（`wasi:filesystem` など）が拒否されるので、許可リストを広げるか、std を使わない書き方を示す必要がある。Emela 0.27 の仕様には stdin を読む標準ライブラリがなく、今は Emela でプロバイダーを書けない。
- JSON の本文: v1 の `host/request` は、クエリとフォームしか送れない。JSON の本文を送る API のために、本文のどこを「パラメータ」として許可と照合するかを決める。
- エディタの位置情報: Graph はソースの位置を持たない。Emela が値に位置を付けられるかは、upstream の課題である。
- AWS の、作成時に決まる ID: 作成前はリクエストタグの条件で絞り、作成後は host が応答から ID を記録して許可に結びつける。
