# ADR 0002 — プロバイダーの契約: 能力の宣言、プロトコル、版の指定

- 状態: Proposed（段階 1 を実装済み。段階 2 以降は本 ADR の合意後に実装する）
- 日付: 2026-11-10
- 対象: Proxmox と mamelet の次に、外部の開発者が書くプロバイダー（AWS など）

## 文脈

これまでのプロバイダーは Mamela のリポジトリの中にあり、次の問題があった。

- **実処理とその説明が別々に書かれていた。** `internal/provider/pve/calls.go` の「この操作はこの API を呼ぶ」という一覧は手書きで、実処理と一致するかはテストで確かめるだけだった。変更のたびに両方を直す必要があった。
- **権限の層に表示用の文章が混ざっていた。** Proxmox の権限は構造化したデータだったが、mamelet の操作は説明文として組み立てていた。エディタの診断や機械的な検査には使いにくかった。
- **宣言ごとの分析が粗かった。** `MayNeed` は、種類ごとに最初のリソースだけを代表にしていた。「この宣言が、この対象に、この能力を要求する」までは追えなかった。
- **外部の開発者がプロバイダーを書く方法がなかった。** 使う人が「どのプロバイダーのどの版を使うか」を指定する方法もなかった。

満たすべき条件:
- 安全側に倒すという Mamela の原則を、外部のプロバイダーにも及ぼす。具体的には次の 3 点である。
  - 権限は最小にする。
  - 宣言していないことはしない。
  - 削除は既定で拒否する。
- 宣言を書いている段階で、必要な権限が分かるようにする。
- Proxmox 専用の作りにせず、AWS の IAM のような別の権限の仕組みにも同じ形で載せられるようにする。

## 決定

### 1. 契約はデータ（マニフェスト）であり、実行時に強制する

プロバイダーは、自分についてマニフェスト（`mamela-provider/v1`、`internal/provider/spec`）で宣言する。

- **扱う種類:** どのリソースの種類を扱うか。
- **操作:** 種類ごとに、どの操作を実行するか。実行しない操作は、その理由を書く。
- **必要な能力:** 操作ごとに、どの能力が要るかを書く。能力はプロバイダー固有の権限名で、次の情報を持つ。

  | 項目 | 内容 | 例 |
  |---|---|---|
  | `capability` | 権限名 | `VM.Allocate`、`apt.install`、`ec2:RunInstances` |
  | `target` | その権限をどこで持つか | Proxmox の ACL のスコープ、mamelet が動くノード、AWS の ARN |
  | `object` | 何に対して使うか | パッケージ名 |
  | `always` | 常に要るか、場合によってだけか | |
  | `standing` | 一度きりの付与か、継続的な付与か | |
  | `limit` | 付与の範囲を狭める条件 | 「承認した apt の変更集合だけ」 |

**マニフェストは説明ではなく、実行時に強制する。** 操作の実行中、プロバイダーは宣言した以上のことができない。Proxmox では `proxmox.Restrict` がこれを担う。宣言にない API 呼び出しやパラメータは、送る前に止まる（`ErrNotSent`。何も起きていないので、結果は分かっている）。したがって、実装に呼び出しを足して宣言を忘れると、その操作のテストがすべて落ちる。一覧が実装から遅れることはない。

「実装から一覧を自動で導く」方法も検討したが、採らなかった（「見送った案」を参照）。

### 2. 分析は宣言のリソースごとに、構造化したデータで行う

`spec.Providers.Analyze` は、宣言のすべてのリソースについて、そのリソースが至りうるすべての操作の要求（`Requirement`）を返す。要求は次のことを持つ。

- 対象のリソース
- 操作
- プロバイダー
- 能力
- 解決した対象（site があれば実名、なければ `<pool>` のような仮の名前と `resolved: false`）
- 条件と理由

plan の段階では、実際の変更と policy の判定から要求を絞る（`lab.Site.PlannedRequirements`）。
- policy が拒否した操作は含めない。
- 自動で修復する場合だけ、継続的な付与にする。
- 承認した変更集合で `limit` を狭める。

文章は CLI の表示層だけで組み立てる。`mamela check --json`（`mamela-check/v1`）は、診断（エディタが使う形: severity、code、message、対象、hint）と要求をそのまま出す。CLI もエディタも、同じ値を使う。

### 3. 版の指定は Pome の依存で行う（段階 2）

プロバイダーは次の 2 つで一組とし、同じ版のタグで出す。

- **作成用の Pome:** Emela で型付きのリソースを作る関数と、`provider.lock` を含む。
- **実行ファイル:** プロトコルを話す。

**使う人の設定は、Pome.toml の依存だけ**になる。

```toml
[dependencies]
"github.com/acme/mamela-aws" = "v0.3.0"
```

Pome.lock と sumdb が Pome の中身の hash を固定する。Pome の中の `provider.lock` は、実行ファイルのプラットフォームごとの URL と sha256 を持つ。`toolchain.lock` と同じ形である。つまり、Pome.lock から実行ファイルまで hash の鎖がつながり、別のファイルで版を指定したり固定したりする必要がない。Mamela は Pome.lock からプロバイダーとその版を知り、実行ファイルを取得して照合する。

Graph（段階 2 で v2 にする）では、各リソースが自分のプロバイダーの source path を持つ。種類の名前はプロバイダーごとの名前空間に入るので、別のプロバイダーと衝突しない。

### 4. プロトコル（段階 2）

プロバイダーは別のプロセスで、stdin と stdout で JSON-RPC 2.0 を話す（LSP や MCP と同じ形）。言語は問わない。

| メソッド | 向き | 内容 |
|---|---|---|
| `describe` | host → provider | マニフェストを返す。Pome にある `manifest.json` と一致しなければ使わない |
| `observe` | host → provider | 範囲内の実状態を返す。観測の時刻は host が付ける |
| `diff` | host → provider | 望む状態と実状態から、リソースごとの変更（差分と操作）を返す。policy の判定と承認は host が行う |
| `apply` | host → provider | 承認された 1 つの操作を、冪等キー（operation ID）とともに実行する。`done`・`failed`・`unknown` を返す |
| `lookup` | host → provider | 冪等キーで、結果不明の操作がどうなったかを調べる |
| `host/request` | provider → host | 外部 API への要求を host に頼む（下記） |

**資格情報は host だけが持つ。** プロバイダーには資格情報を渡さない。外部 API への要求は `host/request` で host に頼む。host は次の順で処理する。
1. その操作のマニフェストが宣言した呼び出しかを確かめる。
2. 資格情報を付ける。Proxmox はトークン、AWS は SigV4 で署名する。
3. 送って、記録する。

プロバイダーの実行ファイルが自分でネットワークに出ても、資格情報がないので何もできない。強制は二重になる。
- host の検査
- 外部の権限の仕組み（Proxmox の ACL、AWS の IAM）

最小の付与は、要求から導く。Proxmox では、今の `mamela lab bootstrap` のようにロールと ACL を作る。AWS では、その plan で必要な action と resource だけを許すセッションポリシーを付け、STS で短期の資格情報を取る。

**policy は操作の名前ではなく効果で判断する。** プロバイダーごとに操作の名前が増えても、host の policy を変えずに済むようにするためである。マニフェストの各操作は、次の効果を宣言する。

- 作成する
- その場で変える
- 再起動する
- データを失いうる
- 置き換える

効果が「データを失いうる」の操作は、既定で拒否する。

### 5. 段階

1. **実装済み**
   - in-process の 2 つのプロバイダー（Proxmox、mamelet）をマニフェストで記述し、`spec` で分析する。
   - Proxmox の呼び出しをマニフェストに制限する。
   - `mamela check --json`。
2. **段階 2**
   - 操作の効果の宣言と、効果による policy
   - Graph v2（リソースごとのプロバイダー）
   - プロトコルと `host/request`
   - Pome と `provider.lock` による配布
   - プロバイダー作者向けの適合テスト一式（宣言どおりにしか呼ばないこと、`unknown` からの再開、冪等性）
   - 今の Proxmox と mamelet を、このプロトコルの上に移す
3. **段階 3**
   - AWS（EC2 の VM）のプロバイダー。ARN を対象にした能力と、セッションポリシーによる最小の付与
   - エディタ向けに、`mamela lsp`（`emela lsp` を包んで Mamela の診断を足す）

## 見送った案

- **実装から呼び出しの一覧を自動で導く。** ありうる経路をすべて実行して記録する方法では、条件つきの呼び出しを網羅できず、漏れは静かに起きる。静的解析は、プロバイダーの書かれた言語に依存する。代わりに宣言を正とし、実装がそれを越えたら送る前に止める（決定 1）。漏れは静かに起きず、必ずテストで表に出る。
- **プロバイダーに資格情報を渡し、外部の権限の仕組みだけで守る。** AWS では成り立つが、Proxmox は一時的な資格情報を発行できない。また、host が呼び出しを記録できなくなる。
- **Emela で直接プロバイダーを書く。** Emela 0.27 の WASM は stdout しか使えず、独自の WIT の import も使えない（emela-lang/emela#56）。宣言は今までどおり副作用のない Emela で書き、実行は別の層に置く。将来 WASM の HTTP（host が仲介する `wasi:http`）が使えるようになれば、プロバイダーを WASM のサンドボックスで動かす案を再評価する。
- **gRPC（Terraform の方式）。** JSON-RPC over stdio のほうが依存が少なく、言語を問わず実装しやすい。また、データがそのまま `mamela check --json` と同じ形になる。

## 未解決

- エディタの位置情報: Graph はソースの位置を持たないので、今の診断はリソースの名前までしか示せない。Emela が値に位置を付けられるかは upstream の課題である。
- AWS のように、対象が実行時に決まる ID（インスタンス ID）になる場合: 作成前はタグの条件で絞り、作成後は ARN で絞る。マニフェストに条件キーを書く欄が要る。
