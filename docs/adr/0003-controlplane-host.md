# ADR 0003 — Control Plane は、自分が適用する宣言の外にある専用のホストに常駐させる

- 状態: Proposed
- 日付: 2026-11-11
- 対象: `mamela serve`（mamelet が revision を取りに来て、報告を送る相手）と、状態データベース

## 文脈

これまでの Control Plane（CP）は、操作する人の Mac で動かしていた。

- `mamela serve` は、Mac のループバックで待ち受ける。
- 各 VM の mamelet は、Mac から張る SSH のリバーストンネル（`mamela lab tunnel`）越しに、それにつなぐ。
- 状態データベース（SQLite）、CA と revision の署名鍵、Proxmox の Token も Mac にある。

検証環境の実機で、次のことが起きた。

- Mac が寝る、LAN から外れる、端末のセッションが切れる（バックグラウンドの時間切れを含む）と、serve とトンネルが止まる。
- 止まっている間、mamelet は報告できない。観測は 10 分で古くなり、plan はすべて止まる（MAM-PLAN-0201）。
- トンネルは VM ごとに張り直す必要があり、VM を足すたびに手間が増える。

一方、CP を、CP 自身が管理する基盤の中に置くことにも問題がある。apply がそのホストの大きさを変えて再起動すれば、apply の途中で CP が止まる。IaC の中で使い続けるなら、CP のホストを自分の plan で変えてはならない。

## 決定

### 1. CP は 1 台の常駐ホストで動かす

- **常駐させるもの:** `mamela serve`。systemd で常駐させる。
- **同じホストに置くもの:** 状態データベース、`controlplane.state_dir`（CA と署名鍵）、site の定義、Token。
- **単一の書き手:** ADR 0001 のとおり、書き手は 1 つの CP だけにする。
- **操作:** plan、approve、apply も、このホストの CLI で行う（SSH）。宣言はホスト上のリポジトリから評価する。ツールチェーンは `scripts/install-toolchain.sh` で入れる（Linux 対応）。
- **将来:** 操作する人の手元から CP に plan を頼む API（mTLS）は、別の ADR で決める。この ADR では、データベースに触れるのは CP ホストの上の `mamela` だけにする。

### 2. CP のホストは、自分が適用する宣言の外に置く

- **自分のホストは変更しない:** site の `controlplane.host` に、CP が動く VM の名前を書く。その CP の plan は、この VM と、その上のリソースへの変更をすべて拒否する（MAM-POL-0308）。宣言に含まれていても、観測と表示だけにする。
- **本番の置き場所:** 管理する基盤の障害範囲の外に置くことを勧める。例えば、別の小さなマシン、または別のクラスタの LXC や VM。Terraform の state の置き場所と同じ扱いで、CP のホストは人が用意する。
- **検証環境:** lab の pool の中に、Mamela で VM を 1 台作り（作るのは移す前の CP）、そこに CP を移してよい。移した後、その VM は 1 の規則で守られる。

### 3. mamelet は LAN から直接 CP につなぐ

- **待ち受け:** `controlplane.url` を CP ホストのアドレスにし、`controlplane.listen` をそのアドレスで待ち受ける。ループバック以外で待ち受けてよいのは、`url` もループバックでないときだけにする。
- **証明書:** サーバー証明書は、`url` のホスト名かアドレスを含むものに作り直す。CA と署名鍵は変えないので、mamelet の信頼の起点は変わらない。
- **認証:**
  - 登録の窓口は、一度きりで期限つきのトークンで守られている。
  - それ以外の要求は、すべて mTLS のクライアント証明書を求める。
  - LAN に出しても、この 2 つは変わらない。

### 4. 既存の mamelet は、署名付き revision で新しい CP に移る

- **知らせ方:** revision に `controlPlane`（新しい CP の URL）を足す。revision は、mamelet がすでに信頼している鍵で署名されている。
- **mamelet の動き:** mamelet は受け取った URL を保存し、次の取得から使う。
- **受け入れる条件:**
  - URL が `https://` であること。
  - 接続先の証明書が、同じ CA で署名されていること。
  - そうでなければ、以前の URL を使い続ける。
- **移す順序:**
  1. 古い CP（Mac とトンネル）で、新しい URL を載せた revision を出す。
  2. mamelet が新しい URL に移る。
  3. データベースと鍵を CP ホストに移し、ホスト上の serve を起動する。

  2 と 3 の間、mamelet は新しい URL につなげない。新しい CP が起動するまで再試行を続けるだけで、取得済みの revision に従い続ける。

## 結果

- 観測は、Mac の状態に左右されなくなる。トンネルも要らなくなる。
- CP のホストを自分の plan で変えてしまう事故は、site の設定と plan の拒否で防げる。
- Token と署名鍵が CP ホストに置かれる。ホストの root を持つ人は、lab の pool の中を変えられる。CP ホストへのログインは、Proxmox の管理者と同じ扱いにする。
- 手元の Mac から plan するには、SSH で CP ホストに入る。手元から直接頼む API は、まだない。
