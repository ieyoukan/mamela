# ADR 0014 — push で同期する（`sync = "push"`）

- 状態: Accepted（2026-11-15）
- 日付: 2026-11-15
- 対象: ADR 0010・0012（mamelacd）、0013（削除の承認）

## 文脈

ADR 0010・0012 の同期は、PR で plan を読み、承認者がコメントで承認し、マージで反映する。家の環境のように、書く人も承認する人も一人で、リポジトリの `main` に直接 push するだけでよい使い方では、PR とコメントが手間になる。Argo CD の自動同期（auto-sync）に当たるものが要る。

## 決定

mamelacd の設定に `sync = "push"` を足す。既定は `"approval"`（これまでの動き）で、push は選んだときだけ使う。

- **先頭が承認になる:** ブランチの先頭のコミットの作者（GitHub が割り当てる login）が `authors` にいれば、その先頭を plan し、変更がある plan は、その作者の名前（`push:<login>`）で承認する。次の poll で apply する（段階が複数あれば、段ごとに繰り返す）。PR もコメントも要らない。結果は commit status に出る。
- **削除は承認しない:** 削除を含む plan は push では承認しない（API も断る。ADR 0013）。commit status に `mamela approve <digest>` を出す。Control Plane のホストで承認すると、次の poll で apply する。
- **承認しないもの:** block のある plan、作者でない（または GitHub のユーザーでない）コミットの先頭は、plan も承認もしない（HeadUntrusted）。
- **PR との関係:** PR の plan とコメントの承認は、これまでどおり動く。`sync = "push"` のときは、作者のマージコミットの先頭も、push と同じに承認される。
- **変わらないもの:** 本体の policy・guard・カタログ・許可、実物が違えば plan し直す、先頭だけを apply する、は同じである。

## 信頼の範囲

- **信頼の根は、ブランチへ書ける人:** コミットの作者は、コミットが言っているとおりで、mamelacd は署名を確かめない。ブランチに書ける人は、作者を名乗れる。したがって `sync = "push"` では、ブランチへの書き込み権限が、変更を承認する権限になる。ブランチ保護で直接 push を禁じていると、この方式は使えない（保護は、force push と削除の禁止だけにする）。
- **mamelacd が乗っ取られたとき:** ADR 0012 の 6 と同じである。承認の身元を信じずに確かめられるのは、署名（ADR 0011 の 10、未実装）だけである。
- **削除:** どちらの方式でも、承認は Control Plane のホストだけである。GitHub 側が乗っ取られても、物は消えない。
- **使う場面:** 書く人が一人で、リポジトリの書き込み権限を自分だけが持つ環境。複数人で運用するなら `"approval"`（PR とレビュー）を使う。

## 検討したが採らなかったもの

- **push でも承認コメントを要求する:** 先頭のコミットにはコメントを付ける PR がない。承認の手間が増えるだけである。
- **削除も push で承認する:** 「GitHub 側が乗っ取られても削除はできない」（ADR 0013）を崩す。
- **コミットの署名を要求する:** 署名の確認は ADR 0011 の 10 で、本体が確かめる形にする。mamelacd が確かめても、乗っ取られれば意味がない。

## 追記（0.3.2、2026-11-17）

- **自動の承認には上限がある:** push が承認した plan の apply が、同じ変更のまま `retry_max + 1` 回続けて戻ってくる（stale になる、または apply したのに同じ plan が出る）と、それ以上は承認しない（`MAM-GIT-0101`）。承認が自動であるぶん、止める側も自動でなければ、世界が変わり続けるとき（別の apply と取り合うとき）に、poll のたびに apply し続ける。止まったあとは、新しいコミットか、ホストでの承認で動く。ADR 0012 の追記を見る。
- **`self_heal = false` はずれの修復すべてに効く:** 以前は、直前の状態が in sync のときだけ、ずれを戻す plan を承認しなかった。ずれを見つけたあとに、waiting・blocked・plan できなかった・失敗を経ても、戻し終わるまで、ずれの plan は push で承認しない（head に「ずれを戻している」記録を持つ）。ホストが承認した戻しの、次の段も同じ。新しいコミットの段は、これまでどおり push が承認する。
- **評価の失敗の理由:** PR のない先頭（直接の push）で評価に失敗したとき、理由は commit status の description とログと（権限があれば）コミットへのコメントに出る。評価器が一時的に使えないだけなら、宣言のせいにせず、`retry` の間隔で評価し直す。
- **作者の身元:** コミットの作者は、login に加えて GitHub の数値 ID も、固定した ID と照合する（ADR 0012 の追記）。名前を引き継いだ別のアカウントのコミットは、自動の承認にならない。
