# 実機レビューに対する修正（2026-11-13）

[利用レビュー](2026-11-12-operator-experience.md)で実測した挙動と、そこから確認した不具合への対応。
検証用 VM は利用者の許可を受けてプロバイダーの明示操作で削除した。事後 guard は境界外の
ゲストに変更がないことを確認した。専用 seed はプロバイダーの cleanup スクリプトが未使用と
判定したもののうち、検証用の完全一致する 1 ファイルだけを削除した。ノード登録・revision・
報告・登録トークンも片付け、監査履歴は残した。

## plan と実行許可

plan は新しい観測対象を、実行許可なしで追加する。既存のサービスの目標値、一度きりの許可、
修復許可、k3s 設定、Control Plane の接続先を候補の宣言で上書きしない。
保護対象のノードについては既存の安全制約を維持し、未宣言のものも含めて許可を失効させる。

`autoStartServices` の有効化・解除は、`automaticStartRepair` の差分と
`configure-service-repair` 操作として plan に現れ、apply で反映する。
実物のサービスが既に稼働している場合も、許可の変更を計画する。
実行するサービスの目標値と k3s の設定は、適用中の保存済み plan から取得する。

ノード ID と登録証明書の serial を計画に結び付ける。名前や VMID が同じでも、再登録後の
エージェントに以前の承認を渡さない。登録の確認と許可の公開は同じ SQLite transaction で行う。

Control Plane の移動も plan から分離した。新しい接続先を使うときは、明示的に
`mamela controlplane redirect --db <state.db> --url https://<host>:<port>` を実行する。
バンドルの DB には移動後の revision を準備し、移動したエージェントが古い serial を受け取らないようにした。
移行手順は [lab.md](../lab.md)。

## 収束の確認

apply は最後に再観測し、宣言全体に残る変更・待機・拒否を表示する。
「この計画の操作が終了した」と「宣言に一致した」を区別する。

GitOps は waiting を pending、blocked / Denied を failure として表示する。
適用後はマージした宣言を再計画し、次の依存段階の変更があるなら新しい digest の承認を待つ。
待機中は次の poll で再観測し、同じ待機状態を毎回コメントしない。
CLI の出力文言を正規表現で読む代わりに、`plan --json` の構造化出力を使う。

## 明示操作の完了とノードの失効

`lose-data` という効果から削除を推定しない。操作後のプロバイダーの観測で対象の不存在を確認し、
完了の記録と所有・ノード登録・許可の失効を同じ transaction にする。
対象がまだ存在する操作では、データを失う操作でも所有記録を保持する。
操作中に所有記録や証明書が変わっていたら、新しい登録を消さずエラーにする。

意図には元の対象、プロバイダー契約、所有記録、登録の identity を保存する。
中断・応答喪失は `mamela act --recover <operation-id> <op> <resource> <pome-dir>` で確認できる。
この経路は lookup / observe だけで、変更要求を再送しない。旧形式の記録は、必要な identity が
ないため自動復旧しない。削除直前に認証済みだった HTTP リクエストも、削除後に古い報告を
書き戻せないよう、報告の保存時に登録をもう一度確認する。

## 表示と Proxmox の固定 IP

- 未宣言の資源は `=` と「別構成のものかもしれない」という説明で保持を表示する。
- approve の案内に `--db` を引き継ぎ、空白や引用符を含むパスもシェルで扱えるようにする。
- README の公開 Pome の代用案内を、現行 API と整合する checkout からの手順に直した。
- mamela-proxmox の guard に、管理範囲内の既存 VM と同じ apply 内の seed の固定 IP 重複を
  拒否する `PVE-0306` を追加した。prefix 長が違っても同じアドレスなら拒否する。
  同じ VM の中断後の再試行は許可する。DHCP の払い出しや管理外のゲストを網羅する IPAM ではない。

## 検証と残る設計

回帰テストでは、plan 後に停止したままであること、候補を変えても既存許可が変わらないこと、
apply 後の修復・許可解除、再登録後の古い承認の拒否、削除後の報告の拒否、GitOps の依存段階の
再承認を確認した。実際の mamelet と偽 OS、localhost の偽 API、実 SQLite を使う。

修正版は既設の Control Plane に配備していない。Mamela の更新後は、以前の計画を再利用せず
再計画する。node provider の契約を 0.2.0 にし、SQLite migration 14 / 15 を追加している。

構成ごとの所有範囲と、宣言から外した資源の `delete / retain` 設定は
[削除の設計案](../design/declarative-removal.md)に残る。今回の不具合修正で、自動削除が
利用可能になったとは扱わない。接続設定の一元化、公開 Pome のリリース、予約 ID の再利用も別の課題である。

## コミット前のレビュー

この修正をコミットする前に読み直し、次を確かめた。

- **直した:** apply の後の再観測に失敗すると、実行した操作が成功していても apply 全体が失敗と表示された。
  操作の結果はそのまま記録し、収束したかが分からないことだけを `MAM-REC-0102` で示すようにした。
- **gitops の作り直しで直す:** マージ済みの PR を、poll のたびに最近の 30 件すべて評価し直していた。
  また、main が先に進んだ後でも、古いマージコミットの plan を承認して apply できた（ADR 0010 の当初の作りから）。
  gitops を `mamelacd` に分けるとき、apply をブランチの先頭に限る（ADR 0011）。
- **残る:** plan が有効な許可を変えなくなったため、宣言から外したサービスの自動起動の許可（standing の repair）は、
  revision に残り続ける。宣言から外れたものの許可を apply で失効させる処理は、
  [削除の設計案](../design/declarative-removal.md)の retain と合わせて入れる。
