# Kubernetes（k3s）の運用を IaC で補償できるか（調査、2026-11-15）

> 実装した（feat/k3s-upgrade）: 「動いているプロセスの観測」（`stale`）、版上げでの再起動（`upgrade-k3s`）、Ready の確認と server、agent の順の 1 台ずつの進め方。下の「足すもの」の 1 と 2 に当たる。

k3s の運用で起きることを並べ、Mamela の今の機能が何を保証し、何を保証しないかを調べた。「検証した」は実機（検証環境の 3 VM）で確かめたこと、「コードから」はコードを読んで言えること、「未検証」は推測である。

## 実機で見つかったこと: 版を上げても動いている版は変わらず、plan は in sync と言う

検証環境の k3s（server 1、agent 2）の宣言で、版と sha256 を v1.37.2 から v1.37.1 に変えて main に push した。

| 観測 | 結果 |
|---|---|
| plan | 3 件の変更。push で承認され、apply された |
| ディスク上のバイナリ | 3 台とも v1.37.1 に置き換わった（`k3s --version`） |
| 動いているプロセス | 3 台とも再起動されず、起動時刻は apply の前のまま |
| Kubernetes の見る版 | 3 ノードとも v1.37.2 のまま |
| apply 後の plan | 「0 changes」（in sync） |

原因（コードから）は 2 つ。

1. mamelet の導入（`InstallK3s`）はバイナリ・unit・トークンを置いて `daemon-reload` するだけで、サービスを再起動しない。再起動は `NodeService` の仕事で、その宣言は「動いていること」だけを見る。すでに動いているので、変更なしになる。
2. `NodeK3s` の観測は、ディスク上のバイナリの sha256 だけを見る。動いているプロセスの版は見ない。

このため、**宣言・ディスク・実行中のプロセスの 3 つが食い違っても、Mamela は収束したと言う**。再起動（または reboot）が起きたとき、予告なしに版が変わる。「宣言どおりであること」を保証する、という Mamela の約束に反するので、k3s の運用で最初に直す。

## 運用の場面と、今の保証

| 場面 | 今 | 備考 |
|---|---|---|
| 新規導入（server、agent、参加トークン） | 検証した | 版と sha256 を固定。3 回の承認で `Ready` |
| 版上げ | 検証した: 動かない（上記） | 再起動と、動いている版の観測がない |
| 版上げの順序（server を先、agent を 1 台ずつ） | なし | plan の依存は「待つ」だけ。健全性の確認で止める仕組みがない |
| 上げる前の確認（全ノード Ready、直前の上げが終わっている） | なし | Mamela は Kubernetes の API を見ない |
| drain と cordon | なし | Kubernetes の操作。Mamela の範囲外にするのが自然 |
| 失敗時の巻き戻し | なし | バイナリは上書き。古いバイナリは残らない |
| server のバックアップ（スナップショット） | なし | k3s の `etcd-snapshot` または SQLite のコピーが要る |
| ノードを足す | コードから: できる | agent の宣言を足す。参加トークンは Control Plane が持つ |
| ノードを減らす | 未対応 | `K3s` の kind に削除の操作がない。VM だけ消えて、Kubernetes にノードの残骸が残る |
| 手で書き換えた unit | 検証した（テスト）: 止まる | `MAM-PLAN-0204`。手で直すまで進まない |
| server のアドレスが変わる | コードから: 入れ直しを承認に出す | |
| OS のパッチと reboot | 範囲外 | reboot は明示的な操作（`mamela act`） |
| 証明書の更新 | 未検証 | k3s が自動で更新する。期限の観測はない |
| 起動引数の変更（traefik など） | できない | 引数は Mamela が決める。宣言からは変えられない |

## 補償の分け方

「IaC で補償する」は、3 つの層に分けて考える。

1. **マシンの層（Mamela の仕事）:** 宣言された版が、ディスクにあり、**動いてもいる**ことを観測して示す。差があれば、再起動を plan に出し、承認を求める。reboot と違って、サービスの再起動は、同じ層の変更である。
2. **順序の層（Mamela の仕事、足す）:** server を先に、agent は 1 台ずつ。各段の前に「全ノードが Ready で、動いている版が想定どおり」を観測の条件にして、満たさなければ待つ（`MAM-PLAN-01xx`）。ADR 0010 の「1 段の終わりは収束ではない」が、段ごとの承認に使える。
3. **クラスタの中の層（Kubernetes と ArgoCD の仕事）:** drain、PodDisruptionBudget、ワークロードの更新。Mamela はここを操作しない。Mamela の仕事は、前提（Ready）を観測することまでにする。

別案として、Rancher の system-upgrade-controller にクラスタの中から版を上げさせる方法がある。ArgoCD で Git に書けるが、バイナリを置き換える主体が Mamela とぶつかる（sha256 の固定が drift として見える）。**採らない**ことを勧める。版の唯一の持ち主は Mamela にする。

## 足すもの（優先順）

1. 観測に「動いているプロセスの版」を足す（mamelet が `/proc/<pid>/exe` の版を見る）。宣言の版と違えば、plan に「再起動」を出す。
2. 版上げを 1 台ずつ段にする（server、agent の順。各段の前に Ready を観測）。
3. 削除（ADR 0013）を `K3s` の kind に足す。ノードを減らすとき、Kubernetes の側のノードも片付ける。
4. server のスナップショットを、版上げの前の観測条件にする。
5. 巻き戻し: 古いバイナリを 1 世代残す（初めは、再び宣言を戻して上げ直す手順だけでもよい）。

Kubernetes の API を見る観測（Ready の確認）は、mamelet が server 上で `k3s kubectl` を読み取りに使う形が最小で、Control Plane が kubeconfig を持たずに済む。

## 実機で試した結果（2026-11-15）

検証環境（mochi の pool `mamela-lab` の中だけ。k3s の server 1 台と agent 2〜3 台、ArgoCD）で、push で同期する運用（`sync = "push"`）のまま試した。見つけた穴は、同じ日のうちに直した（PR #18、#20）。

| 試したこと | 結果 | 直したもの |
|---|---|---|
| 版上げ（v1.37.2 から v1.37.0、v1.37.2 へ。2 往復） | server、agent の順に 1 台ずつ収束。各段は push で承認 | 動いている版の観測、再起動、順番、Ready の確認（#18） |
| 間違った sha256 の宣言 | 何も入らず apply が失敗。binary も k3s も変わらない | 失敗の理由を、ログと commit status に出す（#20） |
| k3s を手で止める | CLI の plan は見つけたが、mamelacd は in sync のままだった | `resync`（検知）、`self_heal`（自動で戻す）（#20） |
| 短い digest でホストの承認 | commit status の 12 桁では `mamela approve` が使えなかった | prefix で足りる（#20） |
| 止まった agent がいるときの版上げ | server は Ready を待った。ただし止まった agent に、server を待たず新しい binary を入れる plan が出ていた | binary があれば、止まっていても server を待つ（#20） |
| VM の再起動 | 再起動後も、宣言した版のまま戻る | — |
| agent の追加（スケールアウト） | push から Ready まで約 7 分、人の操作なし | — |
| agent の削除（スケールイン） | 削除はホスト承認。VM は消えたが、Kubernetes にノードが NotReady で残り、以後の版上げを止めた | Ready の確認を、宣言したノードだけにする（#20）。ノードを消す仕組みは、次の行（#21） |
| agent の削除（2 回目、ノードを消す仕組みつき） | plan が「ノード k3s-s-agent-2 を消す（先に drain）」と「VM を消す」の 2 件を出し、ホストの承認で進んだ。drain で ArgoCD の Pod が server と agent-1 に移り、ノードが消え、そのあと VM が消えた。ArgoCD は HTTP 200 のまま、境界の外のゲストは変わらず | `remove-k3s-node`（MAM-POL-0214）、削除の判定を操作にも広げた（#21） |
| メモリの変更（agent 2 台） | plan が 2 台を同時に再起動しようとした | k3s のマシンの再起動は 1 台ずつ、Ready のあいだだけ（#20）。実機で 1 台ずつ進んだ |
| 同じ名前の agent を宣言に戻す（削除のあと） | 人の操作なしで、約 7 分（push から Ready まで）。新しい VM と新しいノードとして Ready になった。古い証明書や許可は引き継がない | — |
| 中断された適用（API を kill -9） | 次の apply が、世界を見直して完了した | — |
| ArgoCD（Helm チャート）の設定変更 | 承認、書き込み、k3s の Helm が反映（server 1 から 2） | — |

push から収束までの目安（この環境）は、VM の作成が約 1.5 分、k3s の導入が約 1.5 分、サービスの起動が約 2 分、k3s の再起動を伴う版上げが 1 台あたり約 2 分。

## 一から複数ノードの VM を運用できるか、使いやすいか

**運用できる。** 一度だけの準備（人が root）のあとは、宣言を Git に push するだけで、VM の作成、k3s の導入、版上げ、仕様の変更、増減が進む。変更は plan に出て、境界（ノード、pool、VMID、タグ）の外には触れない。

### 良い点
- 変更が必ず plan に出て、何が変わり、なぜで、どう直すかが分かる。理由コードと hint がある
- 安全の装置が効く: 間違った sha256 は入らず、削除はホストの承認、版上げは Ready を確かめ、境界の外の 17 ゲストは変わらなかった
- 失敗と中断が、世界を見直して続きから進む（apply は繰り返してよい）
- push 同期にすると、承認の操作がなくなる（削除だけがホスト）

### 使いにくい点（まだ残っている）
1. **一度だけの準備が重い。** pool、ロール、Token、ACL、イメージ用のストレージの設定を、root で実行するスクリプトで作る。スクリプトは内容を確認してから実行する設計で、安全だが、最初の 1 時間は人の手が要る。`mamela.site.toml` と `mamela.providers.toml`（秘密を含む）も、手で書く
2. **Control Plane のホストの用意が要る。** VM を 1 台用意し、`mamela controlplane bundle` で入れる。mamelet の更新の仕組みがなく、新しい版は各ノードに手で入れた
3. **秘密を渡す方法がない。** ArgoCD に GitHub 認証や、非公開リポジトリの token を足したくても、Git に入れずにクラスタへ渡す方法がない（宣言に書くと Git に入る）
4. **宣言から消した agent の Kubernetes ノードが残る。** drain とノードの削除は、まだ手で行う
5. **失敗のあとのやり直しが「新しいコミット」。** failed の宣言は、新しいコミットが来るまで動かない。`mamela apply <digest>` を手元から繰り返すことはできる
6. **待ち時間が長い。** 1 段ごとに poll（1 分）と apply（約 1.5〜2 分）がかかり、版上げは 1 台あたり約 3 分、4 台で約 10 分。安全のためだが、`interval` を短くすれば縮められる
7. **新しく宣言したものの最初の plan が、長く動いているマシンでは「agent が一度も報告していない」（MAM-PLAN-0110）と出る**（再 plan で直る。メッセージが紛らわしい）

### 使いにくい点の直し方（検討、2026-11-16）

直す順は、「効きが大きく、Mamela 本体を k3s に寄せない（provider と mamelet、mamelacd の中で済む）もの」から。

| # | 使いにくい点 | 直し方 | 大きさ |
|---|---|---|---|
| 7 | MAM-PLAN-0110 が新しい宣言に出て紛らわしい | そのノードが他のリソースを報告済みなら、「このリソースの報告を待つ」（待ち、MAM-PLAN-0108 など）にする。0110 は、そのノードが何も報告していないときだけ | 小（plan のメッセージと条件） |
| 5 | 失敗したあと、新しいコミットが来るまで動かない | mamelacd に `retry`（既定は 10m、最大 N 回）を足す。failed の先頭を、同じ承認のまま、時間を置いて apply し直す。apply は世界を見直して続きから進むので、繰り返してよい。回数を超えたら failed のまま、status に理由を残す | 小（mamelacd の head の状態遷移） |
| 6 | 1 段ごとに poll を待つので遅い | apply が済んだら、次の poll を待たずに plan し直す（段が続くときは、すぐ次の段へ）。mamelet の poll の間隔は、apply の待ちの間だけ短くする | 小〜中（mamelacd の nextStep、mamelet の間隔） |
| 2 | mamelet の更新の仕組みがない | revision に `mamelet: {sha256}` を足す（署名つき）。mamelet は、Control Plane が配る（すでに `GET /v1/mamelet/{sha256}` がある）バイナリを取り、sha256 が revision と一致するときだけ、前の版を残して置き換え、自分を再起動する。起動後に報告できなければ、systemd が前の版に戻す。更新は plan に出て、承認が要る（policy: `update-mamelet`） | 中（新しい op、mamelet の自己置き換え、巻き戻し） |
| 3 | 秘密を Git に入れずにクラスタへ渡せない | Control Plane のホストの `/etc/mamela/secrets/<name>` を、宣言が名前（`secret("argocd-github")`）で指す。plan は名前と内容の sha256 だけを示す（値は出さない）。値は、署名つき revision で、そのノードの mamelet にだけ渡し（参加トークンと同じ経路）、マニフェストの `${secret:<name>}` を書き込むときに置き換える。観測は、置き換えたあとの sha256 | 中〜大（新しい経路。秘密の扱いの ADR が先） |
| 1 | 一度だけの準備が重い | `mamela doctor <provider>`: 読み取りだけで、pool、ロール、Token、ACL、ストレージの有無を調べ、足りないものと、それを作るスクリプトの該当部分を示す。`mamela init` が `mamela.site.toml` と `mamela.providers.toml` の雛形を出す。root のスクリプトは、安全のために人が読んで実行する設計を変えない | 中（provider の契約に点検を足す） |
| 4 | 宣言から消した agent のノードが残る | **実装した**（`remove-k3s-node`） | — |

Mamela 本体を k3s に寄せないために、次を守る。ノードの操作は `NodeK3s` の plan と node provider、mamelet の中だけに置く（核は「削除を含む操作はホストだけが承認する」という一般の規則だけを持つ）。秘密は k3s 専用にせず、「宣言が名前で指し、署名つき revision でノードに渡す」一般の仕組みにする。
