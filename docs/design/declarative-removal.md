# 宣言に追従する削除と、構成ごとの管理範囲

- 状態: 設計案。以下の設定・契約・コマンド動作は未実装。
- 日付: 2026-11-12
- 根拠: 利用者からの「コードに忠実で、削除するか保持するか選びたい」という要望と、
  [実機での利用レビュー](../reviews/2026-11-12-operator-experience.md)。
- 変更対象: ADR 0002 / 0006 の「削除は plan に入れない」という制約。

## 振る舞い

管理下のリソースが宣言から消えたとき、保持するか削除するかを設定で選ぶ。
削除の計画を作ることと、その計画を無人で実行することは別にする。

| on_remove | deletion_approval | 結果 |
|---|---|---|
| retain | 任意 | 実物を保持し、管理上の状態を表示する |
| delete | required | 削除を plan に表示し、その plan の承認後に削除する |
| delete | automatic | 削除を plan に表示し、明示的に許可した範囲では無人の apply / reconcile で削除する |

plan 自体は、どの設定でも削除を実行しない。
新規 stack は `delete + required` を標準にする案を推す。コードに追従し、差分のレビューもできる。
既存環境は移行時に retain として記録し、設定を明示的に変えた場合だけ挙動を変える。
リソースごとの retain も選べるようにする。保護対象や所有権違反は、この設定では解除されない。

retain は、実物と所有記録を残し、その資源への継続的な変更要求を止める意味とする。
適用時に、削除された宣言に由来する修復・インストール許可も失効させる。
別の宣言が同じノードで必要としている許可は維持する。所有記録まで外す操作は別途明示する。

設定のイメージ（まだ読み込めない）:

```toml
stack_id = "web-production"

[lifecycle]
on_remove = "delete"
deletion_approval = "required"
```

## 必要な状態

- **stack の ID:** ディレクトリ名や Git の一時 checkout のパスから導かない、安定した識別子。
- **所属:** resource UID、stack、provider、外部 ID、作成または adoption の記録。
- **適用済みの構成:** plan しただけの候補と、有効化した revision を区別する。
- **削除の情報:** 前回適用した spec、依存、provider のプログラム・カタログ、最後のライフサイクル。
  宣言から消えても、削除対象の identity と設定を失わない。
- **共有依存:** 複数の stack が使うテンプレートなどを記録する。現在の plan にないことだけで消さない。

削除対象は「この stack の適用済み所属にあり、次の適用済み構成にはないリソース」。
provider が観測できる Owned 全体を削除候補にしてはならない。
rename / move は削除と新規作成に誤変換せず、identity の移動として明示できるようにする。

## provider の契約

種類ごとに削除能力を宣言する。Mamela は `lose-data` という効果や操作名から削除を推測しない。
削除能力には、対象 identity、現在の観測から削除差分を作る処理、完了の再観測、拒否条件が必要になる。

ホストは、選択された lifecycle と所属を検証した場合だけ、削除の変更を通常の plan に載せる。
既存の delete の明示操作を呼ぶだけの迂回路にはしない。
所有、guard、許可、前提条件、plan digest に結び付く承認はそのまま適用する。
reboot / adopt は、宣言から消えたことでは実行しない。

パッケージの remove、サービスの stop / disable / unit の削除は同じ意味ではない。
各 kind が「宣言から消える」場合の処理を定義し、未対応なら blocked と理由を表示する。
パッケージ削除は、依存先も含めた実際の変更集合を観測して承認する。

## 実行と復旧

1. 削除の差分、実際に失われる対象、理由、保持する依存を表示する。
2. snapshot と plan digest に結び付け、必要な承認を得る。
3. 直前に所有と外部 ID を再確認する。古い plan や名前の再利用では削除しない。
4. 依存の逆順に、guard → intent 保存 → 許可された要求 → 再観測を行う。
5. 応答喪失時は Unknown として止め、実物を再観測して完了か未送信かを判断する。
6. 削除が確認されたら、所属とノードの登録・実行許可を失効させる。監査履歴は残す。
7. 後段の削除が失敗しても、済んだ削除を繰り返さず残りから復旧できるようにする。

## 受け入れ条件

- delete と retain の両方が、CLI と GitOps で同じ意味を持つ。
- retain を設定したもの、他 stack のもの、Foreign、共有依存は意図せず削除されない。
- 未適用の PR / plan に追加してから消した資源は、削除候補にならない。
- provider の依存自体を宣言から外しても、保存した契約から削除を計画できる。
- 操作途中のクラッシュ、応答喪失、再試行、外部 ID の再利用、古い承認を試験する。
- ノードを同名で再作成しても、以前の証明書やインストール許可を再利用できない。
- waiting / blocked の残る apply を、宣言全体の収束成功とは表示しない。
